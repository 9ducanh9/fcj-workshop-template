*Speakers, organizers, and participants at AWS Study Group Technical Sharing.*

AWS Study Group Technical Sharing helped me approach cloud learning through practical work and clear goals. The four sessions connected project-based learning, prompt engineering, growth mindset, and collaboration methods. Each lesson can be applied directly to how I develop LiveCap during AWS Bootcamp.

## Topic 1 – Long Hoang: Learning AWS through practice and consistency

![Long Hoang speaking at AWS Study Group Technical Sharing](/images/4-EventParticipated/Event1/long-hoang.png)

*[Long Hoang](https://www.linkedin.com/in/huynhhoanglong1812003/) concludes his session with lessons about learning and capability development.*

Long Hoang emphasized learning AWS through hands-on projects rather than memorizing service names and features. When knowledge is tied to a real problem, learners have to understand how components connect, identify limitations, and resolve implementation issues.

Consistency is equally important. Cloud learning is a long process, so progress comes from small repeated steps rather than a short period of intensive preparation. Personal projects and technical blogs turn that process into evidence that can be reviewed, shared, and improved.

For LiveCap, this means prioritizing a realistic MVP, completing core flows, and expanding only after they work. Each deployment, defect review, and documentation update is part of the learning process rather than secondary work after coding.

## Topic 2 – Thinh Nguyen: Why Prompt Engineering Matters

![Thinh Nguyen explaining why Prompt Engineering matters](/images/4-EventParticipated/Event1/thinh-nguyen.png)

*[Thinh Nguyen](https://www.linkedin.com/in/thinhnguyen1211/) explains the problems caused by generic prompts and how clearer communication improves AI output.*

**Why Prompt Engineering Matters** showed that generic prompts often produce generic outputs, waste tokens, increase cost, and create inconsistent results. Prompt engineering is therefore not simply writing a better question; it is a process for communicating requirements clearly to an AI system.

I learned to specify objectives, context, constraints, and output formats. When AI assists with LiveCap coding, documentation, or architecture comparisons, I should provide enough information for the result to be verifiable. I still need to understand the problem and remain responsible for the final decision.

## Topic 3 – Khang Nguyen: Growth Mindset – Ask “Why?”

![Khang Nguyen presenting Growth Mindset and the habit of asking Why](/images/4-EventParticipated/Event1/khang-nguyen.png)

*[Khang Nguyen](https://www.linkedin.com/in/khangck/) discusses asking questions, embracing mistakes, and maintaining a learning mindset.*

**Growth Mindset – Ask “Why?”** highlighted three habits: ask questions to understand causes, treat mistakes as learning evidence, and remain willing to grow. This is particularly relevant to cloud work, where a configuration can function without being secure, cost-effective, or production-ready.

I need to move from asking only “how do I configure this?” to asking “why does this architecture need it?” For LiveCap, I should explain service choices, data flows, failure risks, and trade-offs involving cost, latency, security, and scalability. Fixing a defect is not enough if I do not understand its cause.

## Topic 4 – Thao Nguyen Phuong: Adaptability, Party Mode, and project organization

![Thao Nguyen Phuong speaking about adaptability and Party Mode](/images/4-EventParticipated/Event1/thao-nguyen-phuong.png)

*[Thao Nguyen Phuong](https://www.linkedin.com/in/thao-ngph/) presents the value of adaptability and Party Mode in collaborative project work.*

Thao Nguyen Phuong's session helped me understand how a project can bring multiple perspectives and roles into the same problem-solving process. Adaptability allows a method to change with scale and domain, while Party Mode supports collaboration rather than isolated work.

This connects to the BMAD Method and structured project planning: begin with the problem, clarify requirements, design the architecture, and then implement. For LiveCap, this mindset connects user, business, and technical perspectives and prevents me from selecting AWS services before defining the problem.

## Lessons and personal contribution

After the event, I identified four actions for LiveCap:

1. Build in small steps, prioritize core flows, and maintain consistent progress.
2. Use prompts with clear goals, context, and output criteria when working with AI.
3. Ask “why” before architecture decisions and document the causes of defects.
4. Document requirements, architecture, setup, and learning so others can understand and review the project.

These lessons helped me refine my AWS Bootcamp project into a more realistic MVP. LiveCap should not only run; it should also demonstrate how I learn, explain decisions, and improve the system through each iteration.
